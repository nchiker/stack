# Slice 7 design: sharing linked documents with the partner (2026-11-22)

Status: design, written to be built in stages by cheaper agents, reviewed by a higher-tier agent before release (security: keys, import of foreign data).
Parent documents: `STACK_LINK_CONTRACT.md` ("Sharing with a partner", "Encryption of exports", "Partner devices"), `STACK_ARCHIVE_FORMAT.md`, `RUNBOOK.md`.

## What the two people experience (the bar)
**Owner:** marks a document "Share with partner" once (in Stack, or implicitly because it sits in a folder Filen shares). Nothing else. Changes, moves, unshares and deletes reach the partner by themselves.
**Partner:** meets the owner once, scans one QR code ("Pair with partner"). After that shared documents just appear in Stack search with a "Shared by <name>" badge on the partner's phone and computer. Opening one uses Filen Files; without it the saved text and preview still show. Nothing to type, no folders to pick, no Refresh button.
**Never:** a terminal, a file chooser per document, a key typed by hand, a key in a chat.

## Pieces
1. **Sharing key (once per pair, per direction).** Owner's phone makes a random 256-bit *sharing key* for each partner. "Pair with partner" shows it as a QR on the owner's phone (with a short fingerprint both read aloud); the partner's phone scans it and stores it in its Keystore-wrapped secret store. The key travels only in the QR (in person, no network). The partner's computer never receives the key: it does not read the share archive, it only receives the already-decrypted foreign records through the normal phone-to-computer link sync (item 6). Removing the partner = new key, next publish re-encrypts, old key is forgotten. Both partners can share with each other: each direction has its own key.
2. **Share archive.** One file per owner, `Stack shared.stackshare`, written to the folder the owner shares in Filen. Archive format 4 envelope with one key slot (the sharing key) and a manifest of the shared link records (record, text, preview; never the document file; never `protected` records unless explicitly named; never the owner's other data). Each record carries `link_id`, `owner`, `filen` locator, title, mime, hash, modified, text, preview, and a generation number (the sender's publish counter at that publish); removed or unshared records are listed as tombstones for 30 days. Inside the encrypted manifest the archive also carries an `epoch` (16 random bytes in hex, new with every new or rotated send key) and a monotonic `counter` (per sender, kept next to the send key and raised on every publish, never derived from row revisions). The importer remembers the highest (epoch, counter) it applied per receive key and refuses an archive of the same epoch with a lower counter ("The shared file is older than one already imported."); a new epoch is accepted and resets. Text and previews together are capped at 256 MiB in memory on both sides; a file that is too large or fails for memory is remembered by size and modified time and not retried until it changes. The archive is replaced atomically (write new file, then rename) so the partner never reads half a file.
3. **Where it lives.** A Filen folder `Stack shared` in the owner's drive, shared with the partner by Filen. Stack asks Filen Files for it with one Allow screen, exactly like the existing backup folder grant (`GRANT_BACKUP_FOLDER`): new Filen action `GRANT_SHARE_FOLDER` (creates and shares the folder with the partner's Filen account, returns a persistable tree grant). On the partner's phone, Filen Files offers the received folder with `GRANT_RECEIVED_FOLDER` (read-only tree grant). Until Filen ships these (part F of the runbook) the same code works with a folder chosen once through the system picker, which is also how it is tested. No setup beyond that one Allow screen per phone.
4. **Import (partner).** At app start, when the phone wakes the app, and after Filen reports a change (part F; until then at app start and daily), Stack reads the archive if its modified time or size changed, verifies it decrypts with the sharing key, then applies it: new records as `origin: foreign, access: shared-read`, existing ones updated when the generation is higher, tombstoned ones moved to Recently deleted with the note "no longer shared". The partner's own tags and stacks on a foreign record are kept. Foreign records can be searched, tagged and opened; never edited, moved or deleted at the source; deleting one removes only the local copy.
5. **Open (partner).** The `filen` locator is resolved by Filen Files (`lookup(uuid)` then open in the received-share view, `filen-in`). No call to the owner's app or `link_id`. If Filen or the app is missing: a plain message and the cached text and preview.
6. **Desktop.** The partner's computer gets foreign records through the normal phone-to-computer sync (they are link records with `origin: foreign`), so it needs no Filen client and no folder. The owner's computer needs nothing: its link records already sync from the phone. This removes the "how does the partner's Linux get Filen files" problem for search and preview. Opening the original on the computer waits for a Filen-for-Linux answer and is not part of slice 7.
7. **Privacy.** The archive is always encrypted; the app lock covers foreign records like any link; a protected link is never included unless named; the share archive holds text, so it is as sensitive as the library: the folder is Filen end-to-end encrypted and shared only with the partner.

## Stages (each ends with tests; nothing published without the owner's go-ahead)
- **S7-1 Format and keys (Java + Rust, shared test vectors):** share archive writer/reader, one-slot envelope, tombstones, generation numbers, limits; sharing key storage. Tests: round trip, wrong key, tampering, truncated file, size limits, cross-platform vectors.
- **S7-2 Publish (phone):** "Share with partner" marking, atomic write to the granted folder, republish on change, tombstones on unshare/remove, "Pair with partner" QR display. Runs on the existing sync-changed hook.
- **S7-3 Import (phone):** read, verify, apply as foreign, Recently deleted for tombstones, badge "Shared by", search, detail screen without Open owner path; "Pair with partner" QR scan.
- **S7-4 Sync to desktop:** foreign records and the secret slot through slice 6 cells; desktop shows them read-only with the badge.
- **S7-5 Filen (separate session):** `GRANT_SHARE_FOLDER`, `GRANT_RECEIVED_FOLDER`, change notice, `filen-in` open.
- **S7-6 End-to-end:** two phones (test phone + one emulator or second profile) and a throwaway folder; the real partner run is the final check.

## Open points that need the owner (everything else follows the defaults above)
1. Is the partner's QR meeting in person acceptable (recommended: yes, it is the only moment of friction and it is once)? If not, a remote alternative means typing a code, which this design avoids.
2. Name shown on the badge: the partner's Filen account name, or a name typed once at pairing (default: typed once at pairing, pre-filled).

## S7-4 notes (built 2026-11-22, uncommitted)
Foreign records ride in the existing link cells: the `/content` cell gains `origin`, `shared_by`, `foreign_generation` (all or none), gated by the computer's hello feature `link_foreign` (remembered on the phone in `sync_meta` key `link_foreign_peer`, cleared by a connection reset). Phone schema 16 re-creates the three link sync triggers without the own-only condition; desktop schema 8 adds `origin`, `shared_by`, `foreign_generation`. Unshare travels as trashed/deleted, delete for good as gone. The computer never writes foreign rows (its enable operation reads `origin='own'` only) and archives exclude them. Not run on a phone or a real LAN yet (device checks `LinkSyncChecks.foreignRecords` and the updated `PartnerImportChecks` are compiled only).
